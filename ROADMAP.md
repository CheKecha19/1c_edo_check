# Роадмап доработок

## Cloud.ru VMware — ревизия пользователей тенанта

**Статус на 25.11.2026 — реализовано; ожидает ручной проверки.** Клиент, меню и Excel-отчёт реализованы для одного тенанта. Настройка и ручной тест описаны в [инструкции по запуску](how_to_use.md#cloudru-vmware). Совместимость с площадкой заказчика, права на чтение всех пользователей и заполненность ФИО предстоит проверить. Исходная версия проекта для этого плана — `d24de80`.

**Результат для администратора.** После запуска `python main.py` администратор выбирает VMware и получает в той же Excel-книге список пользователей своего тенанта. Для каждой учётки видны логин, ФИО, кадровое основание, состояние учётки и роли. При необходимости администратор может раскрыть роль до списка прав. Действия над доступом выполняет человек после проверки отчёта.

### 1. Уточнить данные на площадке

- [ ] Начать с одного тенанта VMware Cloud Director (VCD). Из ссылки входа `https://{SITE}/tenant/{TENANT}` взять хост и имя организации. В будущем при нескольких тенантах учитывать хост и организацию в ключах записей и в статусе выгрузки.
- [ ] Получить у администратора доступ с правами чтения пользователей и ролей этой организации. Для детализации прав проверить также чтение состава роли. Количество и состав пользователей сверить с администратором в **Administration → Users**, права выбранной роли — в **Administration → Roles**. Ответ HTTP 200 сам по себе не подтверждает видимость всего тенанта.
- [ ] Выяснить, какие пользователи приходят из LDAP/SAML, где заполнены ФИО, встречаются ли групповые роли, роль «Defer to Identity Provider» и технические записи. Для тестов подготовить обезличенные примеры. Если доступ возможен через внешнюю группу, сверить с администратором, попадают ли все её участники в выгрузку пользователей VCD. Зафиксировать границу покрытия в README.
- [ ] Сохранить в задаче результат проверки: версия API, доступные поля, число записей в интерфейсе и API на один момент, ограничения видимости и способ выдачи токена. Секреты и реальные ответы с персональными данными хранить вне Git.

Для этой задачи применяется API по адресу самого VCD. У личного кабинета Cloud.ru отдельный API на `vmware.api.cloud.ru`, где пользователи и роли запрашиваются по `service_instance_id`. Поля и токены двух интерфейсов нельзя считать взаимозаменяемыми. [Аутентификация VCD](https://cloud.ru/docs/vdc/ug/topics/api/api__auth) · [API личного кабинета](https://cloud.ru/docs/vdc/ug/topics/console__api/console__api__users)

### 2. Получить полный снимок пользователей

Предлагаемые параметры в `config.py` — флаг подключения, HTTPS-адрес площадки, имя тенанта и API Token из переменной окружения. По умолчанию подключение выключено. При явно выбранном VMware и отсутствующем параметре вывести название недостающего параметра в диагностике. Проверять TLS-сертификат, задать тайм-аут. Исключить из логов заголовок авторизации, тело обмена токена и сырой ответ со сведениями о пользователях.

| Шаг | Запрос | Ожидаемый результат |
|---|---|---|
| Версия | `GET https://{SITE}/api/versions` | Выбрать поддерживаемую площадкой версию. Метод списка пользователей появился в API 35.0. Описание конкретной площадки доступно по `https://{SITE}/docs/`. |
| Сессия | `POST https://{SITE}/oauth/tenant/{TENANT}/token` | Передать форму `application/x-www-form-urlencoded` с `grant_type=refresh_token` и `refresh_token=<API_TOKEN>`. Для дальнейших запросов взять `access_token` из ответа. |
| Пользователи | `GET https://{SITE}/cloudapi/1.0.0/users?page=1&pageSize=100` | Заголовки `Authorization: Bearer <access_token>` и `Accept: application/json;version=<VERSION>`. Читать массив `values` на всех страницах, включая отключённые учётки. |
| Права роли | `GET https://{SITE}/cloudapi/1.0.0/roles/{id}/rights?page=1&pageSize=100` | Брать полный идентификатор из `roleEntityRefs[].id`. Прочитать все страницы один раз на уникальную роль в рамках тенанта и запуска. |

[Cloud.ru — обмен API Token](https://cloud.ru/docs/vdc/ug/topics/basic-info/basic-info__api-token) · [Broadcom — параметры списка пользователей](https://developer.broadcom.com/xapis/vmware-cloud-director-openapi/latest/cloudapi/1.0.0/users/get/) · [Broadcom — чтение прав роли](https://developer.broadcom.com/xapis/vmware-cloud-director-openapi/latest/cloudapi/1.0.0/roles/id/rights/get/)

При постраничном чтении сверять номер страницы, количество уникальных ID и итоговый счётчик, если его сообщает сервер. Размер страницы ограничен 128. При изменении счётчиков, повторе страницы или обрыве выгрузки повторить чтение ограниченное число раз. Если полноту подтвердить не удалось, отметить тенант как «Недостаточно данных» и пропустить формирование его кандидатов. Полный успешный ответ с нулём записей означает «Проверен, 0». При истечении сессии однократно обновить токен. Отказ в правах на детализацию одной роли отметить отдельно: успешно прочитанные пользователи и назначения ролей остаются пригодными для кадровой сверки.

### 3. Сопоставить поля VCD с оценкой доступа

| Поле VCD | Что сохранить и как использовать |
|---|---|
| `id`, `username`, `orgEntityRef` | Ключ учётки в контексте площадки и тенанта, логин и организация. Использовать ID для сверки страниц. Две учётки с одним ФИО сохраняются двумя строками. |
| `fullName`, `email`, `providerType` | Отображаемое имя служит входом кадровой сверки. Логин, почта и источник идентификации помогают ручной проверке. При пустом ФИО сохранить строку по ID с результатом «Недостаточно данных». |
| `enabled` | Явное JSON-значение `true` → «Активна», `false` → «Неактивна». Пропуск, `null` или неожиданный тип → «Неизвестно». |
| `locked`, `stranded` | Отдельные признаки состояния входа. `locked=true` означает блокировку после ошибок входа, `stranded=true` — потерю исходного провайдера идентификации. Сохранять пропуски как неизвестные. Для кадрового аудита включённая учётка в обоих случаях сохраняет признак включения. |
| `roleEntityRefs[]`, `isGroupRole` | Сохранить все пары «ID + название роли» и признак наследования от группы. Различать успешно прочитанный пустой список и недоступное значение. Для «Defer to Identity Provider» указать, что фактические разрешения зависят от внешнего провайдера. |

Кадровое основание определяет существующая функция `assessment.assess_account`. Для штатного сотрудника основанием служит актуальная штатка, для исполнителя ГПХ — активная запись в ветке ГПХ AD. Включённая учётка без совпадений в обоих проверенных источниках получает «Проверить доступ». Неоднозначное ФИО, неизвестный статус или отсутствие необходимого источника дают «Недостаточно данных». При однозначном подтверждении из одного источника сбой второго не отменяет основание. Роль администратора сама по себе не определяет ни занятость человека, ни статус его учётки. [Схема пользователя VCD](https://developer.broadcom.com/xapis/vmware-cloud-director-openapi/latest/cloudapi/1.0.0/users/userUrn/get/) · [Cloud.ru — роли и права](https://cloud.ru/docs/vdc/ug/topics/users/users__roles-and-rights)

### 4. Встроить в существующий скрипт

1. В `api_clients/` добавить клиент VCD по образцу клиентов ЭДО. Отделить HTTP, проверку полноты и разбор полей от кадровой оценки. Возвращать строки пользователей и явное состояние источника.
2. В `main.py` добавить выбор «4 — Cloud.ru VMware». В режим «0 — всё» включать VMware при включённой настройке. При выключенной интеграции обычный запуск 1С и ЭДО должен работать без адреса или токена Cloud.ru.
3. В `excel_processor.py` подключить новый источник к `process_excel_data` и передавать в оценку существующие индексы штатки и ГПХ. Учесть три особенности текущего кода: пустые ФИО отбрасываются до оценки, пустой DataFrame считается недоступным источником, а `account_status` повторно интерпретирует текст статуса и не распознаёт строку «Неактивна». Обработать эти случаи явно и покрыть тестами.
4. В «Оценка доступа» сохранить одну строку на учётку с ключом, позволяющим перейти к деталям VMware. В «Источники» указать тенант, полноту и число уникальных пользователей. Для ручного разбора вывести логин, ФИО, статус, флаги входа, назначенные роли и их источник. В лист кандидатов включать только результат «Проверить доступ». Неизвестные случаи направлять на «Недостаточно данных».
5. Детализацию разрешений вынести в отдельный лист «Права ролей VMware» с тенантом, ID и названием роли, ID и названием права. Это сохраняет одну строку на учётку в сводке даже при нескольких ролях и десятках прав. Для недоступной роли показать причину. Права роли описывают её состав; видимость конкретной ВМ или vApp требует отдельной проверки.
6. В how_to_use.md добавить короткую инструкцию по включению, настройке доступа и чтению листов. В примерах использовать только условные адреса, токены и записи.

### 5. Критерии приёмки

| Сценарий | Что должно получиться |
|---|---|
| Выгрузка занимает две страницы, у человека две роли, одна используется ещё одним человеком | Все ID учтены ровно один раз, в сводке по строке на учётку. Назначения сохранены. Права общей роли запрошены однократно на каждую страницу роли. |
| `enabled=true`, `locked=true`, оба кадровых источника доступны, совпадений нет | В отчёте видны блокировка входа и результат «Проверить доступ». |
| Сотрудник найден только в штатке, AD недоступен | «Основание — Штатка». У другой включённой записи без подтверждения — «Недостаточно данных». |
| Пользователь отключён, флаг включения отсутствует, ФИО пусто, ФИО неоднозначно | На отдельных примерах проверить различие неактивного и неизвестного статуса. Записи без ФИО и спорные совпадения остаются видны с ID и логином. |
| Полная выгрузка пуста; в другом запуске не получена вторая страница | В первом случае «Проверен, 0», во втором — источник неполон. Сбой VMware не прерывает формирование отчёта по 1С и ЭДО. |
| Права одной роли недоступны, другая роль унаследована от группы | Видны обе роли, наследование и ограничение детализации. Ошибка чтения прав не превращается в утверждение «прав нет». |
